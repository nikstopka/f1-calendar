# F1 Live Timing Service

Микросервис реального времени для вкладки **Live View**.

## Как это работает

F1 отдаёт live timing бесплатно и без ключа — через WebSocket
`wss://livetiming.formula1.com/signalrcore`. Но браузер читать его напрямую
не может: у F1 нет заголовков CORS, а GitHub Pages — статика без постоянно
работающего процесса. Этот сервис и есть тонкая прослойка.

Данные приходят в трёх разных кодировках, и это главная сложность:

| Топики | Формат |
|---|---|
| `Position.z`, `CarData.z` | base64 + zlib **без заголовка** |
| `TimingData`, `DriverList`, `RaceControlMessages` | JSON, обёртка или без неё |
| `WeatherData`, `TrackStatus`, `LapCount` | голый JSON без обёртки |

Трекер держит только последнее значение на пилота, а не всю историю.

## Где брать стинты и резину

Только из `TimingAppData`. В `TimingData` поля `Stints` **нет вообще** —
проверено на архиве гонки Баку 2026: строка не встречается ни разу за 59 712
строк потока и отсутствует в финальном `TimingData.json`.

Там же обнаружилось, что поле приходит в двух видах:

```jsonc
// поток (jsonStream) — ключ и есть номер стинта
{"Lines": {"63": {"Stints": {"0": {...}, "2": {...}}}}}
// полное состояние (json) — тот же список по порядку
{"Lines": {"63": {"Stints": [{...}, {...}, {...}]}}}
```

Поэтому `{"0":…,"2":…}` — это три стинта, а не два: номер считается как
макс(ключ) + 1. Поток инкрементальный — сообщение несёт только текущий стинт,
поэтому трекер хранит максимум из виденного, а не последнее значение.

## Почему не SignalRClient из FastF1

Он сначала делает `POST .../signalrcore/negotiate`. Этот эндпоинт нестабилен:
наблюдались 20-секундные таймауты подряд, тогда как сам WebSocket отвечал
`101 Switching Protocols` за 0,4 с. Поэтому `livews.py` открывает сокет напрямую
и говорит на SignalR-JSON сам — round-trip через negotiate не нужен.

Ответ `{"type":6}` (ping) нужно отвечать тем же, иначе сокет молча закроется.

## Два режима

**По умолчанию — только live** (`F1_ARCHIVE_FALLBACK=0`). Сервис держит сокет
и отдаёт данные во время трансляции. Между этапами отвечает заглушкой с
`waiting_for_session: true`.

Измерено на Windows: **112 МБ рабочей памяти, ~0 CPU**. Влезает в бесплатные
тарифы с 512 МБ.

**С запасным путём** (`F1_ARCHIVE_FALLBACK=1`) сервис дополнительно
подтягивает последнюю завершённую сессию через `FastF1.Session.load()`, чтобы
отдавать что-то и между этапами. Это требует **~780 МБ** — тариф от 1 ГБ.

История при этом всё равно доступна на сайте: она лежит в
`data/live/sessions/*.json`, собранных заранее из OpenF1.

## Что отдаёт `GET /api/snapshot`

| Поле | Что это |
|---|---|
| `positions` | реальные позиции пилотов |
| `cars[]` | X/Y на трассе, скорость, газ, тормоз, передача |
| `gaps` | отставание (может отсутствовать) |
| `best_laps` | лучший круг каждого |
| `tyres` / `stints` | текущая резина и номер стинта |
| `weather` | температура воздуха и асфальта, влажность, ветер, давление |
| `race_control[]` | флаги, сейфти-кар, сообщения дирекции |
| `track_status` | статус трассы |
| `feed` | состояние сокета: connected, messages, idle_seconds |

Координаты отдаются **сырыми**, а не квантованными. Квантование делает
фронтенд, используя границы из `data/live/circuits/{key}.json`. Если считать
границы по живым данным, в начале сессии машины уедут с карты: пройдена только
часть трассы, и рамка получится намного теснее реальной.

## Проверка

```powershell
pip install -r requirements.txt
python test_livefeed.py    # против настоящего архива F1
python test_poll_loop.py   # машина состояний, без сети
```

`test_livefeed.py` прогоняет через трекер настоящий архив F1 (гонка Баку 2026) и
сверяет результат с `FastF1.Session.load()`:

```
OK  driver 63 X: 876.0 vs 876.0
OK  driver 63 Y: -544.0 vs -544.0
OK  driver 63 position: 1 vs 1
OK  машин в снимке: 22 vs 22          (машины безопасности 241-243 отсеяны)
OK  погода: 26.4 / 39.5 / 41.0 vs те же
OK  статус трассы: 2 vs 2
OK  driver 63 лучший круг: 104.916 vs 104.916
OK  расхождений в номерах стинтов: 0    (22 пилота из 22 совпали)
OK  driver 63 резина: SOFT vs SOFT
память трекера: 0.03 МБ  против  777 МБ у load()
```

Архив кодируется побайтово так же, как живой поток, поэтому тест гоняет тот
же код разбора.

`test_poll_loop.py` не ходит в сеть: он подменяет сокет заглушкой и проверяет
переходы `заглушка → живая сессия → финиш → заглушка`. Именно он поймал то, что
после финиша гонки снимок застывал и фронтенд продолжал рисовать мёртвые
координаты.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `F1_POLL_SECONDS` | `3` | период обновления снимка |
| `F1_ARCHIVE_FALLBACK` | `0` | `1` — включить путь через FastF1 (~780 МБ) |
| `F1_CACHE_DIR` | `.ffcache` | каталог кэша (только для archive-режима) |

## Развёртывание

Подойдёт любой хостинг с Docker и **512 МБ RAM**: Railway Free, Render Free,
Koyeb, VPS.

```bash
docker build -t f1live .
docker run -d --name f1live -p 8080:8080 --restart unless-stopped f1live
```

`Dockerfile` лежит в `live-service/`, контекст сборки — корень репозитория,
поэтому `docker build -f live-service/Dockerfile .`.

### Railway (бесплатно, без карты)

Подключить репозиторий на [railway.app](https://railway.app), указать
Dockerfile `live-service/Dockerfile`, порт 8080. Тариф Free даёт 512 МБ —
ровно столько нужно.

### Render (бесплатно, без карты)

Web Service → Dockerfile, порт 8080. Бесплатный тариф засыпает после 15 минут
простоя и просыпается за ~50 секунд — для календаря это незаметно.

## Подключение к сайту

Прописать адрес в атрибуте `<body>` файла `index.html`:

```html
<body data-live-service="https://ваш-сервис.railway.app">
```

Пустое значение — работа только на статических данных. Если сервис недоступен,
вкладка Live View молча возвращается к ним.

## Ограничения

- **Только во время трансляции.** Между сессиями отдаётся заглушка. История —
  на статических данных сайта.
- **Некоммерческое использование** — как у данных F1 и OpenF1.
- **`gaps` может быть пустым:** поле `GapToLeader` приходит не во всех
  сообщениях. Фронтенд в этом случае показывает число пит-стопов.
- **Проверено на архиве, не на живом эфире.** Сейчас гонки не идут, поэтому
  транспорт проверен (handshake, подписка, ping, переподключение), а приход
  данных `feed` — на архиве. Первый реальный прогон — Сингапур 11 октября.
